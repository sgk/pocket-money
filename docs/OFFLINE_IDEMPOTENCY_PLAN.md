# オフライン対応 + 冪等化 設計メモ

## 目的

- 元帳の更新操作をオフラインでも扱えるようにする。
- 通信断や再送が発生しても、同じ操作が二重適用されないようにする。

## 前提

- 本計画は **単一方式** で実装する。
- 実行時に複数方式を試す挙動は入れない。
- フォールバックは入れない。
- まず安全性を優先し、冪等化を先行実装する。

## スコープ

### 対象（今回）

- 取引API（元帳更新）
  - `POST /api/transactions/expense`
  - `POST /api/transactions/income`
  - `POST /api/transactions/transfer`
  - `PATCH /api/transactions/{tx_id}`
  - `DELETE /api/transactions/{tx_id}`
- フロントの元帳更新UI
  - 新規作成
  - 行編集
  - 行削除
  - 並び替え（dayOrder/日付移動）

### 非対象（初期段階）

- 資産設定・カテゴリ設定・招待・規約同意のオフライン更新
- 競合の自動解決
- 初回ログインのオフライン化

## 全体方針

- 同期は **FIFO 単一キュー**。
- 操作ごとにクライアントが `operationId` を生成し、HTTPヘッダー `X-Idempotency-Key` に設定する。
- サーバーは `(uid, method, path, idempotencyKey)` をキーに実行結果を記録し、同一キーの再実行を拒否せず **同じ結果** を返す。
- キュー再送時は必ず同じ `operationId` を使う。

## 段階実装

## Phase 1: 冪等化基盤（backend先行）

### 目的

- 再送で二重登録が起きない基盤を先に作る。

### 実装

- 取引更新APIで `X-Idempotency-Key` を必須化。
- Firestore に冪等化記録を保存（例: `users/{uid}/idempotencyKeys/{key}`）。
- 記録項目
  - `method`
  - `path`
  - `requestHash`（ボディ正規化後のハッシュ）
  - `statusCode`
  - `responseBody`
  - `createdAt`
  - `expiresAt`
- 同一キー再送時の挙動
  - `method/path/requestHash` が一致: 保存済みレスポンスを返す。
  - `requestHash` が不一致: `409` を返す。
- TTL方針
  - 例: 7〜30日で削除（TTL or 定期削除）。

### 受け入れ条件

- 同じ作成リクエストを3回送っても取引は1件のみ。
- タイムアウト後の同一再送でレスポンス整合性が保たれる。
- 異なるボディで同一キーを送ると `409`。

### 見積

- **450〜650行**

## Phase 2: オフライン閲覧

### 目的

- ネットワーク断でも既存データを表示できる。

### 実装

- Service Worker を有効化（現在の解除処理を削除）。
- IndexedDB に以下を保存
  - `bootstrap`
  - `assets`
  - `categories`
  - `transactions`（フィルタキーごと）
  - `summary`（年月ごと）
- 起動時
  - オンライン: API取得 + IndexedDB更新
  - オフライン: IndexedDBのみ参照
- 画面表示
  - オフライン状態バッジ表示

### 受け入れ条件

- 一度オンライン利用した端末で、オフライン再起動して主要画面を表示できる。
- 取引一覧・資産一覧・月次サマリーが直近キャッシュで表示される。

### 見積

- **600〜850行**

## Phase 3: オフライン元帳更新

### 目的

- 元帳更新をオフライン時にキュー化し、再接続後に安全同期する。

### 実装

- IndexedDBに `operations` ストア追加
  - `operationId`
  - `kind`（create/update/delete/reorder）
  - `payload`
  - `createdAt`
  - `state`（pending/running/failed/done）
- 更新UI挙動
  - オフライン時: キュー投入 + 楽観反映
  - オンライン復帰時: FIFO で順次送信
- 送信時
  - `X-Idempotency-Key: operationId` を必ず付与
  - 成功した操作は `done`
  - 失敗は `failed` で停止（自動解決しない）
- 可視化
  - 同期待ち件数
  - 同期失敗件数

### 受け入れ条件

- オフラインで追加/編集/削除/並び替えを実行できる。
- 再接続後、順序どおり同期される。
- 再送が発生しても重複データが作られない。

### 見積

- **550〜800行**

## Phase 4: テスト・運用固め

### 目的

- 回帰防止と運用性を確保する。

### 実装

- backendテスト
  - 同一キー再送
  - ハッシュ不一致409
  - TTL対象データ
- frontendテスト
  - オフラインキュー投入
  - オンライン復帰同期
  - 同期失敗表示
- 運用
  - 冪等化キーの保管期間ポリシー文書化

### 見積

- **180〜300行**

## 合計見積（テスト含む）

- **1780〜2600行**

## リスクと対策

- リスク: 並び替えの大量更新でキューが肥大化。
  - 対策: 並び替え操作は同日内で圧縮して1操作にまとめる。
- リスク: 端末ローカルの楽観反映とサーバー状態が乖離。
  - 対策: 同期完了後に対象クエリを必ず再取得し、表示をサーバー正とする。
- リスク: 期限切れ冪等化キーの再利用。
  - 対策: キーに作成日時プレフィックスを持たせ、TTL超過は新規操作として扱う。

## 実装順（推奨）

1. Phase 1（冪等化）
2. Phase 2（閲覧オフライン）
3. Phase 3（更新オフライン）
4. Phase 4（テスト・運用固め）

この順により、更新オフライン実装前に「再送安全性」を確保できる。
